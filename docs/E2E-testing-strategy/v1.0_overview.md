E2E Testing Strategy (Playwright)

This document outlines the robust and scalable strategy we've implemented for End-to-End (E2E) testing with Playwright. The core of this strategy is a clean separation between testing authenticated and unauthenticated parts of the application, powered by a global setup and session re-hydration.

This approach ensures our tests are fast, reliable, and decoupled from each other.

1. The Setup Project (auth.setup.spec.ts)

The foundation of our testing is the tests/e2e/auth.setup.spec.ts file.

What it is: A single Playwright test, isolated in its own setup project.

What it does: It runs once before all other tests. Its only job is to:

Navigate to the /login page.

Fill in the credentials for our test user (from dev_seed.ts).

Submit the form and wait for a successful redirect to /dashboard.

Save the entire browser state (cookies and localStorage) to playwright/.auth/user.json.

This file is the only place in our entire test suite that performs a login.

2. Configuration (playwright.config.ts)

The packages/ui/playwright.config.ts file orchestrates this entire flow.

webServer

The webServer command first runs npm run test:setup (which seeds our database) and then npm run dev:full. Crucially, it probes our API server (port 3000), not the UI (5173).

webServer: {
  command: 'npm run dev:full -- --mode e2e',
  url: 'http://localhost:3000', // <-- We wait for the API, not the UI
  // ...
},


This ensures the backend is fully ready before Playwright tries to log in.

projects

We define separate projects for setup, auth, and no-auth tests:

setup Project:

Only runs auth.setup.spec.ts.

*-auth Projects (e.g., chromium-auth):

This is the default for all app tests.

dependencies: ['setup']: Tells Playwright to run the setup project first.

storageState: AUTH_FILE_PATH: Injects the saved user.json into the browser. Every test starts logged in.

testIgnore: 'auth.spec.ts': Explicitly ignores the login test, as it would fail.

*-noauth Projects (e.g., chromium-noauth):

This is only for testing the auth flow itself.

It has no dependencies and uses no storageState.

testMatch: 'auth.spec.ts': Only runs the login/logout test.

This configuration gives us a clean, robust separation of concerns.

3. Application Support (AuthContext.tsx)

For Playwright's storageState to work, the application must be able to re-hydrate its session from localStorage. We've implemented this in AuthContext.tsx.

On App Load: A useEffect hook checks localStorage.getItem('user') and localStorage.getItem('accessToken'). If found, it parses them and sets the isLoggedIn: true state before ProtectedRoute renders.

On Login: The login() function now writes the user and accessToken to localStorage.

On Logout: The logout() function clears the user and accessToken from localStorage.

This makes our app's auth state perfectly compatible with Playwright's session injection.

4. Writing New E2E Tests

For Authenticated Pages (99% of tests)

This is the simple part.

Create your new test file (e.g., tests/e2e/products-page.spec.ts).

Write your test.

Start by navigating directly to the page you want to test (e.g., await page.goto('/products')).

Do not add any login logic. The test will automatically run as an authenticated user.

For Unauthenticated Pages

If you are testing the login, registration, or password reset pages, this is handled by auth.spec.ts. You can add new test.describe blocks to that file.

5. API Mocks

For maximum stability, our tests should mock their API dependencies. We use page.route() in a test.beforeEach block to intercept and fulfill requests.

Success Mock (from customer-360.spec.ts):

await page.route(/.*\/api\/v1\/customers\/cust_abc/, async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    json: { id: 'cust_abc', profile: { name: 'John Doe' }, ... },
  });
});


Failure Mock (from customer-360.spec.ts):

await page.route(/.*\/api\/v1\/customers\/cust_def/, async (route) => {
  await route.fulfill({
    status: 404, // Simulate a "Not Found" error
    contentType: 'application/json',
    json: { message: 'Customer with ID cust_def not found' },
  });
});


This practice makes our tests fast and independent of the live API's state.

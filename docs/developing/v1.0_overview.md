# Development Workflow & Standards

## Overview

This document defines the standardized development workflow for all projects in this codebase. Following this workflow ensures consistency, quality, and maintainability across all features and fixes.

## Branch Strategy

### Branch Naming Convention
```
<type>/<issue-number>-<short-description>
```

**Types:**
- `feature/` - New functionality
- `fix/` - Bug fixes
- `hotfix/` - Critical production fixes
- `refactor/` - Code improvements without behavior changes
- `docs/` - Documentation updates
- `chore/` - Maintenance tasks

**Examples:**
```bash
feature/45-ops-context-setup
fix/128-login-validation
docs/89-api-documentation
```

### Branch Creation
```bash
git checkout -b <branch-name>
git push -u origin <branch-name>
```

## Pre-Development Analysis

### 1. Codebase Context Scanning
Before writing code, understand the relevant code areas:

```bash
# Targeted file discovery
find . -name "*.ts" -o -name "*.tsx" -o -name "*.js" -o -name "*.jsx" | \
  grep -E "(relevant|keywords|components)" | \
  head -15

# Check recent changes in relevant areas
git log --oneline -10 -- <relevant-directory>
```

### 2. Impact Assessment
Document potential affected areas:

```markdown
## Impact Assessment

**Files Modified:**
- [ ] path/to/file1.ts
- [ ] path/to/file2.tsx

**Dependencies:**
- [ ] Internal: component-x, hook-y
- [ ] External: library-z

**Risk Level:**
- [ ] Low (isolated changes)
- [ ] Medium (multiple components)
- [ ] High (core functionality)
```

## Development Phase

### Testing Strategy Matrix

| Component Type | Unit Tests | E2E Tests | Integration Tests | Storybook |
|---------------|------------|-----------|-------------------|-----------|
| Utility Functions | ✅ Required | ❌ Optional | ❌ Optional | ❌ No |
| React Hooks | ✅ Required | ✅ Critical Paths | ❌ Optional | ❌ No |
| UI Components | ✅ Required | ❌ Optional | ❌ Optional | ✅ Required |
| API Routes | ✅ Required | ✅ Required | ✅ Required | ❌ No |
| Complex Business Logic | ✅ Required | ✅ Required | ✅ Required | ❌ No |

### Test-Driven Development (When Applicable)

**Red-Green-Refactor Cycle:**

```javascript
// 1. RED - Write failing test
describe('Feature', () => {
  it('should behave as expected', () => {
    const result = executeFeature(input);
    expect(result).toEqual(expectedOutput);
  });
});

// 2. GREEN - Minimal implementation
const executeFeature = (input) => {
  return expectedOutput; // Hardcoded to pass
};

// 3. REFACTOR - Proper implementation
const executeFeature = (input) => {
  // Real implementation
  return processInput(input);
};

// 4. Verify tests still pass
```

## Shipping Phase

### Standardized Ship Process
```bash
./ship.sh <issue-number> [--skip-e2e] [--emergency]
```

**Script Requirements:**
- Issue number is mandatory for tracking
- Runs full test suite by default
- Creates standardized PR template
- Updates project management system

**Flags:**
- `--skip-e2e`: Skip end-to-end tests (use sparingly)
- `--emergency`: Bypass some checks for critical fixes

### PR Template Auto-Generation

## Post-Shipment Phase

## Issue Management

### Workflow States
```
TODO → IN_PROGRESS → CODE_REVIEW → TESTING → DONE
```

### Transition Commands
```bash
# Start working on issue
gh issue edit <issue> --add-label "in-progress" --remove-label "todo"

# Move to code review
gh issue edit <issue> --add-label "code-review" --remove-label "in-progress"

# Complete issue
gh issue edit <issue> --add-label "done" --remove-label "code-review"
```

## Emergency Procedures

### Hotfix Process
```bash
# From main branch
git checkout -b hotfix/<issue-number>-critical-fix

# Immediate minimal fix
./ship.sh <issue-number> --emergency

# Follow up with proper fix in feature branch
```

### Rollback Protocol
```bash
# Identify problematic commit
git log --oneline -5

# Revert commit
git revert <commit-sha>

# Emergency deploy
./ship.sh revert-<issue-number> --emergency
```

# Kore v2.0: The LaSyncro Co-pilot

* **Status:** v2.0 Released
* **Version:** 2.0
* **Owner:** Platform Team

## 1. 🚀 Kore Philosophy & Guiding Principles

**Kore is the intelligent, conversational co-pilot for LaSyncro.**

It is not a "feature"; it is the new face of the platform's intelligence. Its primary directive is to **save users time and money** by centralizing operations and providing proactive insights.

All development on Kore must follow three guiding principles:

1.  **A Companion, Not a Tool:** Kore is a partner. Its UI, language, and feedback (toasts, confirmations) should always be from the "Kore" persona. This builds trust and creates a "magical" user experience.
2.  **Native-First:** We own our experience. We build our own components (e.g., `ToastProvider`) and prefer native browser APIs (like SSE). We use lightweight, best-in-class libraries (like `fuse.js`) over heavy frameworks.
3.  **Domain-Specific:** Kore is not a general-purpose AI. It is an expert in **e-commerce operations**. Its intelligence is focused, which makes it faster, more accurate, and more useful than a generic tool.
4.  **Transparent:** Kore must never be a "black box." The user should always understand what Kore is *about* to do (`InterpretationBanner`) or *why* it's confused (`OpsClarificationList`). This builds user confidence and safety.

## 2. 🏛️ Core Architecture Overview

The Kore system is comprised of three main parts:

1.  **The Kore UI (Frontend):** The `OpsCommandCenter` component, which lives in the `AppLayout`. This is the user's "Command Bar" and is responsible for rendering the correct UI based on its current "Confidence State."
2.  **The Ops-Intel Engine (Backend):** A background service (`packages/api/src/services/opsIntel`) that runs "Business Rules" (e.g., "Check for Stale Orders") on a schedule. This is the **proactive** brain of Kore.3.  **The Kore Comlink (Bridge):** A **Server-Sent Events (SSE)** stream (`/api/v1/kore/subscribe`) that the backend uses to "push" `ProactiveInsights` (from the Ops-Intel Engine) to the Kore UI in real-time.

## 3. 🚦 The "Confidence Spectrum" (The Core UI Logic)

This is the most critical concept. The `OpsCommandCenter` is a "router" that renders a *different* UI component based on Kore's confidence in the user's query.

This logic is what enables the entire layered system to work as one.

| Confidence State | Trigger | UI Component Rendered | Layer | Status |
| :--- | :--- | :--- | :--- | :--- |
| **Proactive** | `isIdle` + `proactiveInsights.length > 0` | `OpsProactiveList` | **Layer 3** | **Complete** |
| **High** | `confidence > 0.45` | `InterpretationBanner` | **Layer 2** | **Complete** |
| **Medium** | `intent.name === 'clarify'` | `OpsClarificationList` | **Layer 2.75** | **Complete** |
| **Low** | `searchQuery.length > 0` | `OpsResultsList` | **Layer 1** | **Complete** |
| **Default (Idle)**| `isIdle` + No insights | *Nothing* (Clean by Default) | **Layer 1** | **Complete** |
| **Loading** | `isExecuting` | `LoadingState` | N/A | **Complete** |

## 4. Layer 1: The Action Palette (The Foundation)

This is the bedrock of the entire system. Every executable *action* in Kore is an `OpsAction`. The proactive (Layer 3) and conversational (Layer 2) systems are simply "magic" ways of finding and executing these Layer 1 actions.

* **`commandDefinitions.ts`:** The "single source of truth" for all actions.
* **`useOpsCommands.ts`:**
    * Manages the "low-confidence" search.
    * Uses `useFuseSearch` (fed by `useSemanticQuery`) to provide instant, fuzzy-search results.
    * Filters actions based on `OpsContext` (e.g., only shows "Refund this order" if `context.entityId` exists).
* **`useCommandExecution.ts`:**
    * The single, safe hook for *all* action execution.
    * Checks for `requiredPermissions` from `OpsContext`.
    * Handles `isExecuting` state.
    * Fires success/error feedback via our native `useToast` hook.
    * Note: Entity navigation (SearchResult) is handled via `window.location.href`.
* **`useKoreRanking.ts`:**
    * Takes L1 (Actions) and L2 (Entities) results and re-ranks them.
    * Applies boosts based on context, permissions, and personalization (`usePersonalization`).

### Key Data Structure: `OpsAction`

```typescript
// packages/ui/src/components/OpsCommandCenter/types.ts
import { OpsContextState } from 'contexts/OpsContext';
import { NavigateFunction } from 'react-router-dom';

export interface OpsAction {
  id: string;
  name: string;
  description: string;
  keywords: string[];
  icon?: string;
  category: 'safe' | 'destructive' | 'analytical';
  
  // 1. Context rules
  context: {
    pages: string[];           // Where this action is relevant
    needsEntity?: boolean;     // Requires a selected order/customer
    requiredPermissions?: string[]; // e.g., ['refund:write']
  };
  
  // 2. Execution logic
  execute: (
    context: OpsContextState,
    navigate: NavigateFunction
  ) => Promise<CommandResult>;
  
  // 3. Safety & Confidence (CRITICAL)
  preview?: (context: OpsContextState) => Promise<any>; // For data in confirmation
  confirmationMessage?: string | ((previewData: any) => string); // e.g., "Refund $129.99?"
  undoable?: boolean;
}
```
5. Layer 2: The Conversational Engine (The Reactive Brain)
This layer translates natural human language into a high-confidence OpsAction.

Layer 2.0: Natural Language Parser
naturalLanguage/intentParser.ts: The "brain." Takes a query string and returns an Intent object.

naturalLanguage/trainingData.ts: The "dictionary." Maps phrases ("show me orders") to intents ("find-orders").

naturalLanguage/entityExtractor.ts: The "eyes." A set of simple, regex-based functions to find details like dates, order numbers, and statuses (e.g., "yesterday," "unfulfilled").

naturalLanguage/queryExecutor.ts: The "bridge." Converts a high-confidence Intent into a dynamically-generated OpsAction for the Layer 1 useCommandExecution hook to run.

v2.0: Federated & Intelligent Search

* **`useDebounce.ts`:** Prevents searches from running on every keystroke.
* **`useSemanticQuery.ts`:** Expands user queries with synonyms (e.g., "return" -> "refund").
* **`useFuseSearch.ts`:** A fast, fuzzy-search hook that replaces the original `useNativeSearch`.
* **`/api/v1/kore/search`:** A backend endpoint that searches the database for dynamic entities (like customers).
* **`useQuery`:** The `OpsCommandCenter` uses `useQuery` to call the federated search endpoint, combining its results with `useFuseSearch` results.

Layer 2.5: Conversational Memory
This gives Kore a short-term memory to handle follow-up questions.

OpsContext.tsx: The conversation state is stored here:

```typeScript
interface KoreConversation {
  topic: string;        // The last intent, e.g., 'find-orders'
  entities: EntityMap;  // The last entities, e.g., { customer: 'Milad' }
  timestamp: number;    // To auto-clear after 5 minutes
}
```

ConversationHeader.tsx: The UI component that shows "Continuing: Find Orders," so the user knows Kore remembers.

intentParser.ts: Logic is enhanced to check for a follow-up. If query is just "unfulfilled ones," it merges { status: 'unfulfilled' } with the conversation.entities and re-runs the previous conversation.topic.

Reset Logic: A user can type "reset" or "clear" to run the clearConversation command, giving them a safe "escape hatch."

Layer 2.75: The Clarification Flow
This is Kore's "ambiguity handler." It's what Kore does with medium confidence.

intentParser.ts: When a query is ambiguous (e.g., user types "yesterday"), the parser returns a special Intent with name: 'clarify' and a clarificationOptions array.

OpsClarificationList.tsx: A new UI component that renders these options as a list of questions (e.g., [1] Show orders from yesterday?, [2] Show customers created yesterday?).

OpsCommandCenter/index.tsx: The main router renders this component instead of the OpsResultsList or InterpretationBanner. When the user clicks an option, it provides a new, high-confidence Intent to execute.

6. Layer 3: The Proactive Engine (The Co-pilot)
This is the final, most powerful layer, where Kore identifies problems and opportunities for the user.

Backend "Ops-Intel Engine": A service (packages/api/src/services/opsIntel) that runs "Business Rules" (e.g., staleOrderRule) on a cron schedule.

Backend "/api/v1/kore/health": A health-check endpoint.

ProactiveInsight Payload: When a rule is triggered, it generates a JSON payload. This is the "advice" Kore will give.

```TypeScript
// packages/ui/src/components/OpsCommandCenter/types.ts
export interface ProactiveInsight {
  id: string;
  type: 'alert' | 'recommendation' | 'opportunity' | 'celebration';
  title: string;       // e.g., "Stale Order Detected"
  message: string;     // e.g., "Order #100-7890 has been 'Pending' for 3 days..."
  urgency: 'high' | 'medium' | 'low';
  source: 'inventory' | 'orders' | 'customers' | 'marketing' | 'shipping';
  status: 'new' | 'viewed' | 'acted-upon' | 'dismissed';

  // This is the raw data from the backend.
  actionPayload: {
    actionId: string; // e.g., 'nav-order-detail'
    context: Record<string, any>; // e.g., { orderId: 123 }
  }[];
}
```

"Kore Comlink" (SSE): The backend (/api/v1/kore/subscribe) pushes new ProactiveInsight payloads to the frontend in real-time. The OpsContextProvider listens to this stream and adds new insights to the proactiveInsights state array.

OpsProactiveList.tsx: The UI component that renders when Kore is `isIdle` and `proactiveInsights.length > 0`. It displays the `title`, `message`, and `suggestedActions` (as buttons) for each insight.

HealthContext.tsx: Manages the `isKoreHealthy` state by polling the health endpoint, allowing the UI to "gracefully degrade" to L1-only search if the API is down.

Notification Icon: The custom `<KoreIcon />` in the `TopnavbarContent` animates (via `isActive`) to alert the user to `new` insights.
